## 3. เหตุการณ์สำคัญ

### 3.1 แจ้งเตือนผิดว่าระบบล่ม (28/09 23:13)

ยิงทดสอบได้ 403 + `request_logs` ไม่มี traffic → สรุปว่าลูกค้าทุกรายถูกบล็อก

**ของจริง**: เครื่องทดสอบต่อผ่าน **IPv6** เพราะ Cloudflare มี AAAA record
ส่วน `ALLOWED_IPS` เป็น IPv4 ล้วน — ลูกค้าไม่ได้รับผลกระทบเลย

ระหว่างนั้นแนะนำให้ตั้ง `TRUSTED_PROXY_COUNT=3` ซึ่ง**ผิดและอันตราย**
(ทำให้ `ClientIP` อ่าน index 0 ซึ่งเป็นค่าที่ caller ปลอมได้) ค่าที่ถูกคือ **2**

### 3.2 403 ไม่เคยถูกบันทึกลง DB

เช็ค IP เป็นขั้นที่ 3 ส่วน `BeginRequest` เป็นขั้นที่ 8 → คนที่ถูกปฏิเสธไม่เหลือร่องรอย

แก้ด้วยตาราง **`blocked_ip`** (migration `0002`) เก็บเป็นตัวนับ 1 แถวต่อ ip+path+เหตุผล
ไม่ใช่ 1 แถวต่อ request จึงไม่บวมและไม่เป็นช่องขยายผล DoS

เปิดดูครั้งแรกก็ได้คำตอบทันที: ลูกค้า DigitalOcean สิงคโปร์รายหนึ่งต่อผ่าน IPv6
ถูกบล็อกไปแล้ว **328 รายการใน 8.5 ชั่วโมง** และมี IPv4 อีก 3 ตัวที่ไม่อยู่ใน allowlist

ต่อมาเพิ่ม `first_chain`/`last_chain` (migration `0003`) เก็บ IP ทุกตัวที่เห็นในคำขอ
ทำให้แยกออกทันทีว่าเข้ามาทาง Cloudflare หรืออ้อม origin ตรง ๆ

### 3.3 integration test ที่ไม่เคยถูกรัน

เทสต์ชุดนี้อยู่หลัง build tag `integration` มาตลอดโปรเจกต์ พอรันกับ DB จริงครั้งแรกเจอ 3 บั๊ก:

1. `RecordBlocked` ใส่ `NULLIF` ให้คอลัมน์ `NOT NULL` → เหตุผล `missing_trusted_header`
   ไม่เคยถูกบันทึกเลย **โดยที่ 403 ยังตอบปกติ ไม่มีใครเห็นว่าผิด**
2. `JSONOrRaw` ปล่อยไบต์ `0x00` ที่ JSONB ปฏิเสธ → `BeginRequest` ล้ม → handler ตอบ 503
   (บั๊กเก่า ไม่เกี่ยวกับงานรอบนั้น)
3. `TestMigrateIsIdempotent` ผูกกับจำนวน migration เป็นเลขตายตัว

วิธีรัน: `TEST_DATABASE_URL="<dsn ที่ dbname=postgres>" go test -tags=integration ./internal/...`
(มันสร้าง DB ชั่วคราวเอง)

## 6. บทเรียน

### 6.1 DB ที่ว่างไม่ได้แปลว่าถูกบล็อก

`request_logs` ว่างเข้าได้สองทาง: "ทุกคนถูกบล็อก" กับ "ไม่มีใครยิงเข้ามาในช่วงนั้น"
ต้องมีตัวนับแยก (`blocked_ip`) ถึงจะแยกออก — **403 ไม่เคยถึง `request_logs`**

### 6.2 `upstream_timeout` ที่สั้นแทบไม่มีประโยชน์เลย

```
timeout ขณะรอ response → WroteRequest = true → Classify คืน fatal → ไม่ retry
```

การตัดเร็ว**ไม่ได้ทำให้ไปลอง url ถัดไป** มันแค่แปลง "รายการที่ช้าแต่จะสำเร็จ"
ให้กลายเป็น "ออเดอร์ที่ไม่รู้สถานะ" — ได้แต่เสีย

`upstream_timeout` มีประโยชน์เฉพาะตอนเชื่อมต่อไม่ติด (DNS/TCP/TLS) ซึ่ง `WroteRequest=false`
→ retryable — แต่ช่วงนั้นถูกจำกัดด้วย timeout ของ Go transport อยู่แล้ว

**ตัวที่คุ้มครองลูกค้าจริงคือ `rpc_timeout` กับ `x-deadline` ไม่ใช่ `upstream_timeout`**

### 6.3 อย่าตั้งค่าจากภาพนิ่งของการกระจายที่กำลังขยาย

ประเมิน "ยังไม่ต้องแตะ" ผิด **สามครั้งในคืนเดียว** ด้วยวิธีเดียวกัน คือดู percentile
ณ ขณะนั้นแล้วสรุปว่ามีที่ว่าง โดยไม่ดูว่ามันกำลังเคลื่อนที่

```
16:30  p99 1,285ms
20:30  p99 8,188ms    ← โตหกเท่าใน 4 ชั่วโมง
```

ขยับเพดาน 7s → 12s ก็ยังชนอีกภายใน 45 นาที **ต้องแก้ที่หลักการ ไม่ใช่ขยับทีละขั้น**

### 6.4 เทสต์ที่ไม่เคยรันคือเทสต์ที่ไม่มี

integration test รออยู่หลัง build tag มาตลอดโปรเจกต์ พอรันครั้งแรกเจอ 3 บั๊กทันที
**ควรรันก่อน deploy ทุกครั้ง**

### 6.5 ก่อนสรุปว่า deploy ทำพัง ให้เทียบเวลากับ `schema_migrations.applied_at`

เมื่อ 29/09 01:50 `success` หยุดนิ่งแล้ว `failed` พุ่ง ดูเหมือน deploy ทำพัง
แต่ลำดับเวลาพิสูจน์ว่าไม่ใช่:
```
01:50:06  success สุดท้าย
01:50:27  DEPOSIT_CLOSE ครั้งแรก   ← ก่อน deploy 1 นาที 45 วินาที
01:52:12  deploy
```
`DEPOSIT_CLOSE` / `WITHDRAW_CLOSE` คือ **payment provider ปิดรับตามเวลาทำการ**

### 6.6 กับดัก IPv6 + Cloudflare

Cloudflare มี AAAA record ให้ทุก domain โดยอัตโนมัติ เครื่องที่เปิด IPv6
จะเลือกต่อผ่าน IPv6 เอง แต่ `ALLOWED_IPS` เป็น IPv4 ล้วน → **403 ทั้งที่ config ถูกหมด**

แยกให้ออกด้วย `curl -4` เทียบกับ `curl -6` และ **IPv6 ของ droplet เปลี่ยนได้เอง**
(ของเครื่องทดสอบเปลี่ยนภายในคืนเดียว) การเอามาใส่ allowlist ทีละตัวจึงไม่ยั่งยืน
ทางแก้คือปิด IPv6 ที่ Cloudflare

## 8. คำสั่งที่ใช้บ่อย

```sql
-- สถานะรวม บรรทัดเดียว
SELECT (SELECT count(*) FROM request_logs r JOIN attempt_logs a USING (trace_id)
        WHERE a.outcome='fatal' AND (a.http_status IS NULL OR a.response_body IS NULL
              OR a.response_body='')) AS ต้องตามเก็บ,
       (SELECT count(*) FROM request_logs WHERE attempt_count>1) AS retry,
       (SELECT count(*) FROM request_logs WHERE status='pending'
        AND created_at<now()-interval '2 min') AS pending_ค้าง;

-- รายการที่ต้องตามเก็บ พร้อมรายละเอียด
SELECT to_char(r.created_at AT TIME ZONE 'Asia/Bangkok','DD/MM HH24:MI:SS') AS เวลา,
       r.group_name, r.request_body->>'amount' AS ยอด, r.business_ref,
       coalesce(a.http_status::text,'-') AS quickpay, a.duration_ms, a.error_message
FROM request_logs r JOIN attempt_logs a USING (trace_id)
WHERE a.outcome='fatal' AND (a.http_status IS NULL OR a.response_body IS NULL
      OR a.response_body='') ORDER BY r.created_at;

-- ใครถูกบล็อก เข้ามาทางไหน ใช้เครื่องมืออะไร
SELECT client_ip, path, reason, count,
       last_chain->>'host' AS เข้าทาง, last_chain->>'ua' AS เครื่องมือ,
       last_chain->>'cf_ipcountry' AS ประเทศ
FROM blocked_ip ORDER BY count DESC;

-- เวลาตอบสนองรายชั่วโมง
SELECT to_char(created_at AT TIME ZONE 'Asia/Bangkok','DD HH24:00') AS ชม,
       count(*), round(avg(total_ms)) AS avg,
       percentile_disc(0.50) WITHIN GROUP (ORDER BY total_ms) AS p50,
       percentile_disc(0.95) WITHIN GROUP (ORDER BY total_ms) AS p95,
       percentile_disc(0.99) WITHIN GROUP (ORDER BY total_ms) AS p99,
       max(total_ms) AS max
FROM request_logs WHERE created_at > now() - interval '24 hours'
GROUP BY 1 ORDER BY 1;
```
