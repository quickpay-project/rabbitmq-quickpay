## ⚠️ ข้อจำกัดของข้อมูลชุดนี้ — อ่านก่อน

ตัวเลขทั้งหมดนับจาก **รายการที่เดินทางมาถึง backend สำเร็จเท่านั้น**

| ชั้น | ใครบันทึก | อยู่ในข้อมูลชุดนี้ไหม |
|---|---|---|
| ลูกค้ายิงเข้า queue | RabbitMQ | ❌ ไม่มี |
| queue พยายามยิงไป backend (รวมที่ล้ม) | `withdrawauto_logs` ฯลฯ ใน DB `mq` | ❌ **ตารางว่าง — ดูหมายเหตุท้ายไฟล์** |
| มาถึง backend | `system_logs` | ✅ มี |
| สร้างรายการสำเร็จ | `deposit_orders` / `withdraw_orders` | ✅ มี |

**รายการที่ตายตอน TLS handshake ไม่ทิ้งร่องรอยไว้ในข้อมูลชุดนี้เลยแม้แต่แถวเดียว** ตัวเลขจริงที่ระบบต้องรับมือจึงสูงกว่าที่เห็น แต่สูงกว่าเท่าไหร่ยังไม่รู้

## 4. เส้นทางที่ผ่าน queue โดยเฉพาะ

นับจาก `system_logs` ที่ `func_name = INTERNAL:CONTROLLER:CS_WITHDRAW_CREATE_AUTO`
(คือ request ที่ `conswithdrawauto` ยิงเข้า backend สำเร็จ)

| สถานะ | 7 วัน |
|---|---:|
| มาถึง (RECEIVED) | **1,963** |
| สำเร็จ (COMPLETED) | 1,937 |
| ล้ม (FAIL) | 26 (1.3%) |

**~1,963 จากรายการถอนทั้งหมด ~19,500 ใน 7 วัน** → เส้นทาง queue คิดเป็นประมาณ **10% ของรายการถอนทั้งหมด**

เฉลี่ยแล้ว = **280/วัน ≈ 12/ชม. ≈ 0.2/นาที**

สาเหตุที่ล้ม 26 รายการ (ไม่ใช่ปัญหาเครือข่าย):

| สาเหตุ | จำนวน |
|---|---:|
| `Duplicate withdraw request` (ตัวกันซ้ำ 1 นาทีทำงาน) | ~16 |
| validation error (`customer_order_id is required` ฯลฯ) | ~10 — เป็นการทดสอบด้วย payload ไม่ครบเมื่อ 09-23 19:02–19:04 |

## 5. ผลต่อการตั้ง worker

ใช้กฎของ Little: `จำนวนที่ทำงานพร้อมกัน = อัตราเข้า × เวลาต่อรายการ`

| สถานการณ์ | อัตราเข้า | ถ้า 1 request ใช้ 2 วินาที | worker ที่ต้องใช้จริง |
|---|---:|---:|---:|
| ถอนผ่าน queue — เฉลี่ย | 0.2/นาที | × 2 วิ | **0.007** |
| ถอนผ่าน queue — พีค | 3.5/นาที | × 2 วิ | **0.12** |
| ฝาก+ถอนรวม — พีคนาทีหนักสุด | 103/นาที | × 2 วิ | **3.4** |

เทียบกับที่ตั้งไว้ใน `.env`:

| ตัวแปร | ค่าปัจจุบัน | ใช้กับ consumer |
|---|---:|---|
| `WITHDRAW_LIMIT` | 300 | `conswithdraw` **และ** `conswithdrawauto` (ตัวละ 300) |
| `DEPOSIT_LIMIT` | 500 | `consdeposit` **และ** `consdepositauto` (ตัวละ 500) |
| **รวม goroutine ถ้าเปิดครบ 4 ตัว** | **1,600** | |

**เกินความต้องการจริงประมาณ 100–500 เท่า**

### ข้อควรระวังก่อนลดค่า

ตัวเลขข้างบนคำนวณจาก **เวลาต่อรายการ 2 วินาที** ซึ่งเป็นสมมติฐาน ยังไม่เคยวัดจริง
ถ้า backend ตอบช้ากว่านั้นมาก (เช่น 30 วินาที) จำนวน worker ที่ต้องใช้จะเพิ่มตามสัดส่วน

**ต้องวัด p95 ของเวลาตอบกลับจาก backend ก่อน แล้วค่อยตั้งค่า** — สูตร:

```
worker ที่ควรตั้ง = (อัตราเข้าพีค ต่อวินาที) × (p95 เวลาต่อรายการ เป็นวินาที) × 3   ← เผื่อ 3 เท่า
```

ตัวอย่าง: พีค 1.7/วิ × p95 5 วิ × 3 = **26 worker** ก็เพียงพอ

## 6. หมายเหตุ: ทำไมข้อมูลฝั่ง queue ถึงไม่มี

ตาราง `withdrawauto_logs`, `withdraw_logs`, `deposit_logs`, `depositauto_logs` ใน DB `mq` **ว่างเปล่า**

สาเหตุที่พบจากการอ่านโค้ด — **ยังเป็นจริงกับเส้นทางเก่า (`rabbitMQ/cons*.go`) ณ วันที่แก้ไขเอกสารนี้**:

| # | สาเหตุ | หลักฐาน |
|---|---|---|
| 1 | ไม่มีใครสร้างตาราง | ไม่มี `CREATE TABLE` สำหรับ 4 ตารางนี้ที่ไหนเลย — migration ของ Gateway v2 (`internal/store/migrations/0001_init.sql`) สร้างแต่ `message_group`, `message_group_url`, `request_logs`, `attempt_logs` **ไม่ครอบ 4 ตารางเก่า** |
| 2 | INSERT ล้มแล้วเงียบ | ทุก call site ยังเขียน `_, _ = insertXxxLog(...)` — ทิ้ง error ทั้งคู่ |

### เส้นทางใหม่ (MQ Gateway v2) แก้เรื่องนี้แล้ว

`internal/store/` มีระบบ migration จริง (`migrate.go` + `schema_migrations`) และเก็บ log ลง
`request_logs` / `attempt_logs` ซึ่งออกแบบมาให้ตอบคำถาม "พยายามยิงกี่ครั้ง ล้มกี่ครั้ง ที่ URL ไหน" ได้โดยตรง

**แปลว่าข้อมูลที่เราขาดอยู่ในเอกสารนี้ จะมีให้ใช้เมื่อ traffic ย้ายมาเส้นทาง Gateway v2**
จนกว่าจะถึงตอนนั้น ต้องพึ่ง stdout ตามด้านล่าง

**ข้อมูลสำรองที่ยังพอใช้ได้:** stdout ของ container มี `log.Printf` ทุกครั้งที่ยิงและทุกครั้งที่ล้ม

```bash
# จำนวนที่พยายามยิงทั้งหมด
docker logs <container> --since 7d | grep -c "🌐 Withdraw Auto API URL"

# จำนวนที่ล้มด้วย TLS handshake
docker logs <container> --since 7d | grep -c "TLS handshake timeout"
```

เอาตัวเลขแรก **ลบ** ด้วย 1,963 (ที่มาถึง backend) = **จำนวนที่หายไประหว่างทาง**

## วิธีดึงข้อมูลชุดนี้ซ้ำ

รันบน DB ของ `quickpay_backend` (อ่านอย่างเดียว):

```sql
SET default_transaction_read_only = on;

-- รายชั่วโมง
WITH d AS (SELECT date_trunc('hour', created_at) h, count(*) n
           FROM deposit_orders WHERE created_at > now() - interval '7 days' GROUP BY 1),
     w AS (SELECT date_trunc('hour', created_at) h, count(*) n
           FROM withdraw_orders WHERE created_at > now() - interval '7 days' GROUP BY 1)
SELECT to_char(coalesce(d.h,w.h) AT TIME ZONE 'Asia/Bangkok','MM-DD HH24:MI') AS hr,
       coalesce(d.n,0) AS deposit, coalesce(w.n,0) AS withdraw,
       coalesce(d.n,0)+coalesce(w.n,0) AS total
FROM d FULL JOIN w ON d.h=w.h ORDER BY coalesce(d.h,w.h);

-- อัตราต่อนาที
WITH allm AS (
  SELECT date_trunc('minute', created_at) m FROM deposit_orders WHERE created_at > now()-interval '7 days'
  UNION ALL
  SELECT date_trunc('minute', created_at) m FROM withdraw_orders WHERE created_at > now()-interval '7 days'),
per AS (SELECT m, count(*) n FROM allm GROUP BY m)
SELECT round(avg(n),1) AS avg_per_min,
       percentile_disc(0.50) WITHIN GROUP (ORDER BY n) AS p50,
       percentile_disc(0.95) WITHIN GROUP (ORDER BY n) AS p95,
       percentile_disc(0.99) WITHIN GROUP (ORDER BY n) AS p99,
       max(n) AS max_per_min
FROM per;

-- เส้นทาง queue โดยเฉพาะ
SELECT status, count(*) FROM system_logs
WHERE created_at > now() - interval '7 days'
  AND func_name = 'INTERNAL:CONTROLLER:CS_WITHDRAW_CREATE_AUTO'
GROUP BY 1;
```
